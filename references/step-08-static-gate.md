# 步 08：过静态门

## 目标

检查全部正式状态的肤色与高光接线；按实际资源绑定签名分组做反射对照，并把七项检验的完成状态核清。

## 进入条件

- [ ] 步 04 的修补/回环通过，或已核验依赖未变并复用其通过记录。
- [ ] 步 07 的每份正式 HLSL 都有本次内容对应的严格编译通过结果，可由缓存复用。
- [ ] 步 02 用户选定的状态已逐一对应到步 07 正式文件；检查版不属于正式状态。

## 操作

### 先按本次改动决定重验范围

新 mod、新原 PS、游戏/RabbitFX 更新或缺少可信基线时，执行本步完整检查。已有通过记录时按下表执行；“记录”可来自当前会话、临时产物或工作区台账，不额外要求普通用户写一套报告。

| 本次改变 | 需要重验 | 可复用的检查 |
|---|---|---|
| 只改透肉/高光强度等参数 | 改过的正式 PS 严格编译、实际资源与对应反射组；游戏看相关外观 | 未变的原 PS 忠实修补、肤色/UV/烘焙、门控/键位审计；相关首次实机结果按步 11 复用 |
| 换光腿图、网格、UV 或身体染色 | 受影响来源检测；C 重烘与质量检查；相关交付绑定及游戏对照 | 没变的原 PS 修补；没变的 shader 可复用编译结果 |
| 改 INI 接线、状态或范围 | 相关状态/资源/门控检查、实际影响范围和切换；HLSL 变了再验证它 | 未变的肤色/烘焙与编译结果；范围未变的其它 draw 不重复测 |
| 只改说明文字/链接 | 文档 lint；命令改了核对 CLI；相关既有文档测试 | 不跑算法全套、shader 编译、mod 流程或游戏；关键流程歧义才做一次低模型阅读检查 |
| 修改 skill 的处理脚本 | 相关回归；跨脚本公共逻辑改动时跑一次全套 | 普通 mod 使用不跑 skill 的整套 unittest；通过且代码未改不再跑第二轮 |

复用前核对内容 SHA、工具/编译条件及相关环境与通过记录一致，不能仅凭文件名或“上次成功”。没有证据或改变了该项依赖就重验受影响项。首次雨雪没测过，不能借参数小改冒充已有验收。

### 编译一次，检查各自的问题

步 07 生成器、本步交付检查和反射命令使用同一个 `<编译缓存目录>`（工作目录下独立 `compile-cache`）并传 `--compile-cache`。脚本只复用同源码、同编译条件且完整性校验通过的成功字节码；输入/编译器变化、依赖无法追踪或缓存损坏时重新编译。缓存只节省编译，不跳过颜色、INI、资源与原 PS 对照；不是“所有验证已通过”的通行证。生成器与反射命令统一使用 `--compiler d3dcompiler`，与交付检查的系统 DLL 路线一致。外部 fxc 因实际 DLL 身份不能可靠核对，保守重编译；没有缓存时仍正常检查，不额外手工跑一次 fxc。

缓存是可重建的临时数据，不放进 overlay 或交付 ZIP。跨目录副本不承诺命中；避免仅为验证复制同一 HLSL 多次。以下现有检查按上表范围执行一次。

1. 先核对状态名单：把步 02 每个用户选定材质状态对应到一个正式文件，不得只列启动状态。步 09 接线完成后，对每个目标 draw 的全部正式状态一起运行以下命令；只有一个状态就删除第二个 `--shader`，更多状态逐一追加 `--shader`。同一 draw 有多种原 diffuse 时，每份颜色报告各运行一次，仍列全该 draw 的正式状态。此检查需要真实 INI 及引用文件，不在步 09 之前把它记作通过：

   ```powershell
   python scripts/check_sheer_delivery.py --ini "<交付INI>" --shader "<正式状态一>" --shader "<正式状态二>" --colour-report "<颜色报告>" --original-ini "<原mod ini>" --source-route <来源路线> --style-index <外观下标> --compile-cache "<编译缓存目录>"
   ```

   只有用户明确取消高光时，才用下列命令替代；不是报错时的修复办法：

   ```powershell
   python scripts/check_sheer_delivery.py --ini "<交付INI>" --shader "<正式状态一>" --shader "<正式状态二>" --colour-report "<颜色报告>" --original-ini "<原mod ini>" --source-route <来源路线> --no-style-switch --compile-cache "<编译缓存目录>"
   ```

   颜色报告中的原始 INI 和输入文件须仍可读取且 SHA 一致。改过输入就回步 06 重生成；不改 JSON 绕过身份核验。复杂调用分支输出未验证时，按下面“失败结果如何处理”补证；未验证不等于 PASS。

2. 按检查器输出的资源绑定签名分组名单，每组取它列出的一个正式代表文件。步 09 前可以先对已生成文件做本项，接线后再确认分组名单没有增加；已通过且未改动的组不重复。不要传 `--matrix`，不要把检查版传进去：

   ```powershell
   python scripts/reflect_check.py "<一个状态文件>" --original "<底子>" --require <必须槽列表> --out "<反射目录>" --compiler d3dcompiler --compile-cache "<编译缓存目录>"
   ```

3. 从上到下读完每组的 C1–C8；最后一行必须是“结果:全绿”。`--require` 中每个槽都要出现“必须反射出 … PASS”，只在 HLSL 里声明但被优化掉不算通过。任一正式状态丢了采样时，交付检查必须失败，即使首个状态的反射通过也不能放行。

4. 汇总已有结果，不按这张清单把脚本再跑一遍；每项按上述改动范围取得或复用一次证据：

   | # | 检验 | 通过证据 | 所在步骤 |
   |---|---|---|---|
   | 1 | `vs` 与 `ps` 两个门控值有人定义且无冲突 | 两次 `audit_filter_index.py --gate` 均通过 | 步 03 |
   | 2 | 忠实修补、严格编译与编译回环 | `fix_decompiler_defects.py` 退出码 0，回环无不等 | 步 04 |
   | 3 | 每份生成 PS 严格编译 | `build_sheer_ps.py` 对每份输出打印通过 | 步 07 |
   | 4 | 肤色来源保真 | B 优先并确认光腿源与目标 UV 对应；C 表面距离及 VP2 通过；非单色或不确定禁止 A | 步 01、06 |
   | 5 | 每种资源绑定签名的正式代表反射对照 | 每组 `reflect_check.py` 全绿 | 步 08 |
   | 6 | 全部正式状态的肤色、ini 结构与默认高光切换 | `check_sheer_delivery.py` 退出 0 且无未验证项；仅已证实的适配限制允许按下文逐项补证；所选状态名单与输入一致 | 步 08、09 |
   | 7 | zip CRC 与条目数 | `pack_mod.py` 自检通过 | 步 10 |

5. 当前工作区若另有 BASELINE、manifest、逐条读回 zip 或报告规则，把它们作为工作区检验追加执行；它们不替代上表七项，也不改变本 skill 默认清单。

6. 同签名状态不重复 reflect；不同签名不能借首个状态过门。检查版 reflect、8 档编译矩阵及无故追加全盘扫描不属于本流程。颜色 JSON 是当前验收的临时证据，不要求普通用户长期保存报告；工作区另有台账规则时执行。

## 判定

### 失败结果如何处理

`FAIL`、非零退出、未验证、文件缺失和身份失配都表示对应检查未完成。先逐条读取诊断及其指向的实际产物；不能因为其它检查成功、原 mod 也有类似写法、错误很多或模型认为“这是工具限制”，就跳过错误或称交付完成。

| 诊断分类 | 必须完成的动作 | 可报告的结果 |
|---|---|---|
| 产物错误或输入缺失/失配 | 修复实际文件或重新生成真实输入证据，重跑受影响检查 | 依据新输出报告；旧失败记录仍保留 |
| 怀疑检查器不支持合法布局 | 先定位检查器拒绝条件，再核对它拒绝的实际 INI/命令；原因未证实前仍算未验证 | “尚未验证”，不能进入打包/启用 |
| 已证实为检查器适配限制 | 扩展检查器并通过相关回归，或完成下列独立补证；不能删原条件、改 draw 操作或改报告来换 PASS | 如实区分“通用检查器仍 FAIL”与“对应项独立验证通过” |

**独立补证不是一句“人工看过”。** 只有检查器适配限制可以走此路；实际产物错误、缺输入、缺实机反馈不能这样豁免。对每个未支持项必须同时具备：

1. 对应诊断、检查器限制的具体依据，以及本次 INI/网格/状态的映射；不能用一份泛化解释覆盖所有错误。
2. 针对实际交付文件执行的可复现验证。接线项须覆盖 section 归属、全部调用条件的可达性、目标状态命中、非目标状态逐字回退、实际资源绑定；对受影响路径比较改前/改后绘制命令。只数条件、只检查字符串存在或只重跑编译不算补证。
3. 验证器必须能拒绝本次错误版本；没有错误版本时，用隔离副本构造与该诊断相关的错误并确认拒绝。不得为测试修改现役 mod。
4. 每个原失败项都有结果，且输入身份一致；仍有一项未解决就保持未验证。全部补证完成后才进入后续步骤；补证不改变通用工具原返回码，也不代表实机通过。

已有对应验证满足以上内容时直接复用，不要求再建一套工具、重跑全套测试或重复实机基线。默认不留报告的环境可在当前上下文给出证据位置与结论，工作区要求报告时按工作区保存。

| 看到什么 | 结论 | 下一步 |
|---|---|---|
| 最后一行全绿，所有 `--require` 槽 PASS | 正式状态通过静态门 | 进步 09 |
| C2 编译失败 | 正式 HLSL 不可安装 | 回步 07，按第一条编译错误修正 |
| C4 资源或采样器多出未允许槽 | 接入了未说明的绑定 | 回步 06/07 核对肤色槽；确认有意新增后列入 `--require` 重跑一次 |
| C4 少槽、C5 cb 不同或越界 | 原材质功能可能丢失 | 回步 04 核对忠实修补，不用 `--allow-missing` 放行 |
| C6/C7 签名不同 | 输入或输出 ABI 被改坏 | 回步 07 恢复底子签名 |
| probe 的反射资源少 | 检查版提前返回造成优化 | 不运行这项；改用正式状态文件 |

## 失败处理

| 症状 | 原因 | 修法 |
|---|---|---|
| `--require` 后的路径被当成槽位 | 必须槽列表没有在路径前结束 | 把 `--out "<反射目录>"` 放在槽列表之后，并确认列表只含 `tN/sN/uN` |
| 原 PS 原文严格编译失败，但 C1 有内嵌 asm | 原始反编译仍有缺陷 | 回步 04；不能把 C1 的声明来源 PASS 当成忠实修补通过 |
| 只有指令数不同 | 编译器优化导致浮动 | 指令数只参考；按 C1–C8 与最终结果判定 |
| 工作区检查与默认清单冲突 | 工作区有更严格交付规则 | 执行工作区规则并保存它要求的证据 |
| 交付检查退出 2 | 缺文件、参数或颜色报告版本不符 | 按错误中点名的输入补齐；报告回步 06 生成 |
| nonuniform/unknown 配 A，或某状态肤色采样为 0 | 实际产物丢失逐像素肤色 | 回步 06 确认 B/C，步 07 重建该状态；不得改报告或改为常数 |
| 缺 cycle、错误下标、未定义变量或零高光增益 | 默认高光切换未接通 | 根据诊断回步 07/09 修指定参数或段；不得改用 `--no-style-switch` |
| `D10` | 从任何 TextureOverride 出发，沿 run / 回调 ref 链都到不了控制段 | 把 run 写回原 draw 所在行，保留原调用链和原条件；不要新加条件。检查器会沿链继承 ib/vb 并按分支分别核对，嵌套布局不需要补证 |
| `D28` 点名一条带条件的路径（例如 `$lod_level == 1`）绑了另一套缓冲 | 那个档位也能进入替换，而烘焙/颜色报告只对应当前档位的网格 | 把区分该档位的 mod 自有变量加进门控（例如 `$lod_level == 0 &&`），重跑；不改绑定、不删路径 |
| `D29` | run 不在原 draw 那一行，或调用段其它命令 / 条件被改动 | 调用段其余命令恢复原样，只把原 draw 那一行换成 run；没给 `--original-ini` 时只出现 INFO，不算通过 |
